# Tessera — project rules

Tessera (working codename) is a clean-room, from-scratch reimplementation of a game client
that is compatible with data files from *The Lord of the Rings Online*™. It reads a user's
own, legally-obtained install **in place and read-only**. Rust workspace, wgpu renderer,
GPL-3.0-or-later.

## Clean-room boundary (non-negotiable)

The repo has two zones:

| Zone | Paths | Who may read it |
|------|-------|-----------------|
| **Dirty room** (research) | `research/`, the research clones (`~/.cache/tessera/clones` or `$TESSERA_CLONES_DIR`), dirty scratch dirs (`~/.cache/tessera/scratch/*/dirty`, `$TESSERA_RE_DIR`), anything under a scratchpad `clones/` dir, game binaries, disassembly | Spec writers only |
| **Clean room** (implementation) | `crates/`, `apps/`, `fuzz/`, `tools/` | Implementers, working **only** from `docs/specs/` |

- `docs/specs/*.md` is the **only** interface between the two. Specs are prose and tables of
  functional facts (field layouts, enums, algorithms described in words). No copied code, no
  pseudo-code transliterated from someone else's source or a decompiler.
- Implementation sessions must **not** open `research/`, third-party LOTRO/AC/DDO source
  trees, or decompiler output. If a spec is missing a fact, stop and add a TODO to the spec
  (`> **OPEN:** ...`) instead of looking it up in dirty material.
- Never paste decompiled or disassembled client code into an implementation session.
- Most published LOTRO tools are unlicensed (all rights reserved) or GPL/AGPL. Never copy
  their code; extract facts into a spec instead. Cite the source in the spec's provenance table.

## Content rules

- Never commit game data: no `.dat`/`.datx`, extracted textures, meshes, sounds, strings,
  maps, item databases, Lua UI files, fonts, or Daybreak/Turbine binaries or keys.
- Test fixtures are **synthetic** (generated by our own code) or original CC0 content.
- Real-data tests read only `TESSERA_GAME_DIR` (auto-detection serves the apps, not the
  tests) and skip themselves, reporting "passed", when it is unset. Export it
  (`export TESSERA_GAME_DIR="$(cargo run -q -p tessera-dattool -- detect --path)"`) before
  claiming real-data results. They must never write to the install directory.
- Never hard-code Daybreak/SSG hostnames, keys, or bulk data tables extracted from the client
  binary. Anything of that kind must be loaded at runtime from the user's install. Numeric
  constants that define an algorithm (hash multipliers, salts, thresholds, unit scales) are
  allowed when a spec records them with `BIN` provenance (`docs/decisions/0012-numeric-constants.md`).

## Naming

Identifiers, crate names, UI strings and docs must not use LOTRO/Tolkien/Daybreak/Turbine
marks as product names (see `docs/LEGAL.md`). Referring to "LOTRO data files" for
compatibility in plain prose is fine. Format-level terms like "DID" or "landblock" are fine.

## Engineering conventions

- Rust edition 2024. Toolchain = the exact version pinned in `rust-toolchain.toml` (CI uses
  it too; bump it on purpose and fix new lints in the same commit). MSRV = `rust-version` in
  `Cargo.toml` (1.90; `apps/explorer` declares 1.95 for eframe/egui). `cargo fmt`,
  `cargo clippy --workspace --all-targets -- -D warnings` and `cargo test --workspace` must
  pass.
- Parsers treat all input as hostile: no panics on malformed data, bounded allocations,
  `Result` with a `thiserror` error type per crate. Every parser has a fuzz target in `fuzz/`.
- Library crates use `tracing` for logs, never `println!`.
- Commits are signed off (`git commit -s`). Commits that implement a format or protocol carry
  a `Spec-Ref: docs/specs/<file>.md#<section>` trailer; commits touching `crates/`, `apps/`,
  `fuzz/`, `tools/` or `docs/specs/` carry `Clean-Room-Role: spec | review | implementation`;
  AI-assisted commits carry an `Assisted-by:` trailer (`tools/check-dco.sh`).

## Working across machines and sessions

- Git is the only shared state (`docs/decisions/0007-multi-device-workflow.md`). Claude
  memory, transcripts and scratch dirs do not travel, so record decisions in
  `docs/decisions/` and progress here or in the roadmap, then commit and push.
- Setup and hand-off steps: `docs/DEVELOPMENT.md`. Check a machine with `tools/dev-setup.sh`.
- Continue the roadmap with the saved workflow `.claude/workflows/tessera-milestone.js`
  (one milestone per run, then review, commit, push; it refuses M8). Dirty-room research
  clones go in `${XDG_CACHE_HOME:-~/.cache}/tessera/clones` (`tools/fetch-research-clones.sh`
  or `tools/dev-setup.sh --fetch-research`), never inside the repo.
- Machine-local, git-ignored: `.cargo/config.toml` (build cache location) and
  `TESSERA_GAME_DIR`. Never commit either.

## Layout

- `crates/dat` — `.dat`/`.datx` container: header, extent/block layer, B-tree directory, zlib, archive set, DID routing
- `crates/formats` — record decoders on top of `dat`: primitives, string tables, surfaces, property sets, setups, landblocks, distant-landscape sectors, entity descriptors, appearance (wardrobe) records, items, avatar bodies (race table), script tables and scriptlets with the idle/walk/run clip resolver, instanced-content views
- `crates/props` — property registry, values, property sets, enum mappers, DID maps
- `crates/text` — string tables, StringInfo resolution, substitution, markup
- `crates/assets` — prioritised worker pool, cancellation, decoded-asset cache
- `crates/material` — materials, surfaces, texture chains, dye, layered icons
- `crates/mesh` — mesh records → engine-neutral vertex streams (static and skinned), mesh library, character/object assembly (`assembly`: body parts by priority, worn and held items, dye layers)
- `crates/havok` — clean-room reader for the Havok tagfile subset in the archives: skeletons (in 0x04 setups) and clips (0x05: spline-compressed, interleaved, annotation tracks, reference frames)
- `crates/anim` — skeletons, clip binding and sampling, blending, root motion, attach points, bone sliders, skinning palettes, animation scheduler on the asset workers
- `crates/entity` — the client's entity store (decision 0008): entities, transforms, network IDs, render/animation handles, landblock membership, per-frame change lists
- `crates/wstate` — WLib class library and WState object graph; player-character and game-control views
- `crates/wvm` — script machine of the class library (WLib bytecode): code-block decoder, load-time rules, disassembly, census and cross-references
- `crates/world` — coordinates, landblock streaming, residency budget, area lookups
- `crates/terrain` — heightmap meshing with LODs, crack-free seams, height queries
- `crates/physics` — collision and movement (M4.5): terrain/ceiling collision, cells, per-landblock collision sets with a BVH (water planes and liquid boxes included), capsule sweeps, the character controller (fixed 1/60 s step, constants owned here); depends only on `formats` and `props`, `world` may depend on it (decision 0013)
- `crates/particles` — particle runtime: the shared random generator, deterministic simulation of particle systems (0x39) with emitters, caps and controllers, billboard vertices, fork-effect lifetimes (not simulated), effect start/attach/stop/linger rules (`particles.md`, `particle-runtime.md`)
- `crates/input` — actions, contexts, keymap file, free-fly and walk controllers
- `crates/settings` — Tessera's own settings file
- `crates/install` — locate installs (env var, Steam libraries, common Wine prefixes), identify versions
- `crates/net` — transport-agnostic session layer, a local sandbox backend and the test-server backend (`remote`)
- `crates/protocol` — Tessera's own network protocol: messages, framing, codec, session state machines, key pinning, QUIC setup
- `crates/render` — wgpu renderer (mesh/material/terrain pipelines, GPU skinning, golden-image tests, the particle pipeline)
- `crates/script` — Lua 5.1 plugin host
- `apps/dattool` — CLI for inspecting archives (`info`, `ls`, `cat`, `extract`, `validate`, `snapshot`, `diff`, ...)
- `apps/explorer` — egui asset browser (textures, strings, properties, icons, meshes, character viewer and animation browser, headless `--sheet`, particle preview of 0x39 records and `--particles DID --sheet`)
- `apps/client` — the game client binary (world walker with an animated avatar, placed NPCs and a `--crowd` load test; `--server` joins a test server)
- `apps/server` — `tessera-server`, the headless test server for Tessera's own protocol
- `apps/loadtest` — `tessera-loadtest`, load, soak and hostile-input tests
- `docs/specs` — clean-room specifications; `docs/decisions` — decision records;
  `docs/checklists` — visual/owner checklists; `docs/` — legal, process, roadmap, tooling, development
- `research/` — dirty-room notes, the verified resource catalogue and `clones.txt`
